# Ревью безопасности авторизации — 2026-09-06

## Дополнение 2026-09-07: email/password MVP

Ниже сохранены исторические находки первого этапа. В текущем рабочем дереве уже
включена Bearer-dependency, закрыты старые кодовые входы и включена проверка секрета
webhook. Это не означает, что приложение готово к публикации.

В этом этапе исправлено восстановление: сервер хранит метод аутентификации сессии
(миграция 79), требует свежий Telegram/Google-вход, не допускает замену email,
атомарно меняет хеш и отзывает остальные сессии. Вход по паролю повторно читает
credential после блокировки аккаунта; старый пароль не должен выдать сессию после
завершившегося reset. Исправлен savepoint при конкурентном создании throttle.
Валидационные ответы auth-роутов не возвращают пароли/токены. Middleware больше не
повторяет изменяющий HTTP-запрос при ошибке соединения. Адрес Telegram-напоминания
определяется по проверенной identity, а не внутреннему ID аккаунта.

Проверки: изолированные SQLite/API-тесты, клиентские store-тесты с синтетическими
ответами, ESLint и Vite build. Это не E2E на Android и не PostgreSQL concurrency test.
Миграции подготовлены и проверены только на disposable SQLite; production не затронут.

Открытые ограничения перед публичным выпуском: автоматический refresh на клиенте,
защищённое хранение токенов, изоляция офлайн-данных/очередей при смене аккаунта,
распределённые лимиты регистрации/challenge, явное подтверждение входа в боте,
проверка Google/Telegram redirect и возврата на Android. Email используется как
неподтверждённый логин, не как доказательство владения почтой. Без заранее привязанного
Telegram/Google восстановление в MVP отсутствует. Совпадающие email не объединяют аккаунты.

Актуальный порядок развёртывания: [DEPLOYMENT.md](../../api/auth/DEPLOYMENT.md).

## Исторический снимок первого этапа

Объём: текущие способы определения пользователя, бот, кодовый вход, привязки, перенос данных,
сессии нового ядра и миграция. Проверка кода и синтетические тесты; это не аудит работающего
сервера и не проверка всех API проекта. Production-запросы, сообщения и изменения данных не выполнялись.

**Заключение:** новое ядро можно передавать на этап интеграции. Публиковать приложение как
имеющее полноценную авторизацию пока нельзя. Старые маршруты активны; перечисленные ниже
уязвимости не исправлены простым добавлением `api/auth/`.

## Проверка новой основы

Реализовано и проверено локально:

- Telegram HMAC и Google RSA-подпись/claims; неправильные issuer, audience, nonce, presenter,
  подмена подписи, просроченные/будущие credentials отклоняются. Транспортные ошибки не раскрывают детали.
- Привязка по `(provider, subject)`, без поиска по email. Конфликт не перемещает identity и
  не возвращает чужой профиль. Для link требуется недавний вход в исходный аккаунт.
- Непредсказуемые токены, в БД только hashes; проверяются назначение, срок, сессия и disabled-account.
  Повтор refresh отзывает его семейство, отзыв фиксируется до ошибки и не затрагивает другое устройство.
- Одноразовый provider proof; account/session/proof откатываются вместе при неудачной выдаче.
- Уникальные ограничения БД; тест двух одновременных refresh; строгая dependency игнорирует
  поддельный `X-User-ID` даже рядом с валидным токеном другого аккаунта.
- Аддитивная миграция, неизменные resource IDs/строки, идемпотентность и rollback всей схемы при ошибке marker.
- Исторический guest ID не выдаёт данные настоящему Telegram-пользователю с совпавшим номером:
  возвращается `legacy_account_review_required`. Старые `is_guest=false` являются лишь кандидатами;
  их историческую достоверность невозможно доказать по этой БД без внешних подтверждений.

Новые модели не входят в автоматический `create_all_tables`, новые маршруты не включены,
старые сессии и коды не преобразуются в доверенные credentials. Действующее поведение приложения
не переключено частично. `api/auth` не импортирует `api.main` и не начинает подключение к DB при импорте.

## Оставшиеся требования перед релизом

1. Закрыть P1-находки выше одновременно с переключением клиентов. Изменение только заголовка
   в UI или только одного FastAPI dependency не создаёт безопасный полный flow.
2. Реализовать persistent challenge, подтверждение link и привязку ответа к исходному устройству.
   Передаваемый в Google validator `expected_nonce` должен читаться из проверенного server state;
   приём nonce из самого запроса создаст обход. Сам `VerifiedIdentity` не является HTTP-схемой.
3. Ограничить callbacks/redirect, защитить login/link от CSRF и подмены сессии. Проверять
   webhook secret constant-time до любого действия, брать Telegram subject только из проверенного Update.
4. Настроить распределённые rate limits, очистку истёкших сессий, ротацию секретов, redaction
   Authorization/cookie/initData/кодов в HTTP-логах и трассировке.
5. Хранить refresh в HttpOnly cookie / Android Keystore, сериализовать обновление на клиенте.
   Не отправлять токены через URL и не повторять refresh автоматически после потерянного ответа.
6. Повторить миграцию, rollback и конкурентные сценарии на отдельном PostgreSQL. SQLite
   подтверждает логику и ограничения, но не является проверкой PostgreSQL row-lock поведения.
7. Проверить реальные Android/web/Mini App входы, возврат из внешнего приложения, потерю сети,
   старый APK, logout, смену аккаунта с pending edits и поздними ответами прошлой сессии.

Из-за отсутствия зарегистрированных HTTP v2 маршрутов нельзя утверждать, что эти интеграционные
меры уже действуют. План и порядок работ: [AUTH_V2.md](../ARCHITECTURE/AUTH_V2.md).

## Проверки, выполненные в этом этапе

28 тестов `test_auth_foundation.py` прошли. Дополнительно выполнены `py_compile`, проверка
CLI `--help`, просмотр PostgreSQL DDL без подключения и итогового diff. Не запускались
production-запросы, миграции рабочей базы, реальные провайдеры и UI/APK. Локальный PostgreSQL
и тестовый DSN отсутствовали; psql/postgres/docker не найдены в PATH.

Первая попытка SQLite-тестов встретила ограничение Windows на доступ к приватным временным
каталогам Python 3.14; тесты перенесены на отдельные случайные файлы в `scratch`, которые
удаляются после каждого успешного теста. Это была ошибка тестового окружения, не миграции.

Основные протоколы сверены с [Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app),
[Telegram webhook secret](https://core.telegram.org/bots/api#setwebhook),
[Google ID token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
и [OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).
