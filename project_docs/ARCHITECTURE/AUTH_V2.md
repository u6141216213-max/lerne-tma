# Авторизация Lerne: архитектура и передача следующему этапу

Дата обновления: 2026-09-07. Auth v2 подключён к API и общему web/Android-клиенту,
но production-готовность не подтверждена. Актуальные ограничения и миграции 76–79:
[DEPLOYMENT.md](../../api/auth/DEPLOYMENT.md).

Email/password MVP не отправляет письма и не подтверждает владение почтой.
После регистрации предлагается привязать Telegram к текущему аккаунту. Восстановление:
вход через заранее привязанный Telegram/Google → профиль → новый пароль в течение
5 минут. Сервер проверяет метод и давность сессии, сохраняет email и отзывает остальные
сессии атомарно. Существующие сессии после миграции 79 имеют NULL method и для reset
не подходят. Добавление первого email/password использует `/email-password/link`,
восстановление существующего — `/email-password/set`; email профиля не является credential.

Этот документ фиксирует реализованные границы и обязательный порядок интеграции.
Результаты ревью: [AUTH_SECURITY_REVIEW.md](../reports/AUTH_SECURITY_REVIEW.md).
Legacy-входы по `X-User-ID`, числовому guest ID и шестизначному коду выведены из
эксплуатации. Оставшиеся deployment-пункты ниже обязательны до публикации.

## Решение об аккаунтах

`TMAUser.user_id` становится внутренним ID аккаунта Lerne. Его значение у существующих
пользователей сохраняется. Колоды, папки, карточки, история обучения, коллаборация и
локальная база `LerneLocalDB_<user_id>` не перенумеровываются при добавлении провайдера.

| Объект | Назначение |
| --- | --- |
| `TMAUser` | Существующий профиль и неизменный ID владельца ресурсов |
| `TMAAuthAccount` | Состояние доступа к этому профилю; отключение аккаунта и кандидат на старый Telegram ID |
| `TMAAuthIdentity` | Уникальная пара `provider + subject`, связанная с одним аккаунтом |
| `TMAAuthSession` | Отдельная сессия устройства; дата подтверждения входа, абсолютный срок, отзыв |
| `TMAAuthToken` | SHA-256 случайного access/refresh-токена, назначение, срок и отметка использования |
| `TMAAuthProof` | Использованный отпечаток подтверждения провайдера; защита от повторного предъявления |
| `TMAAuthChallenge` | Одноразовое подтверждение login/link: hash секрета устройства, state, nonce, PKCE и результат проверки |

В первой версии поддерживается один Telegram и один Google на аккаунт. База обеспечивает
уникальность `(provider, subject)` и `(account, provider)`, FK и каскадное удаление auth-сессий.
Google определяется по `sub`, Telegram — по проверенному Telegram ID. Email, имя, аватар и
номер телефона не используются для поиска совпадающих аккаунтов или автоматической привязки.

Новые аккаунты получают случайный отрицательный ID между `-2**52` и `-10**12`.
Он точно представим в JavaScript и не пересекается с положительными Telegram ID.
Отрицательные временные ID карточек в Dexie принадлежат другому пространству сущностей.
Перед включением нужно адаптировать потребителей, которые пока считают любой account ID
Telegram ID: уведомления бота, ссылки, поиск участников по числовому идентификатору.

## Что реализовано

| Файл / функция | Контракт |
| --- | --- |
| `api/auth/providers.py` | Проверка сырого Mini App `initData`; проверка Google ID token официальной библиотекой `google-auth` |
| `login_verified(proof)` | Находит аккаунт по проверенной привязке или создаёт новый; возвращает сессию |
| `link_verified(access_token, proof)` | Добавляет провайдера к текущему аккаунту после недавнего входа; не переносит чужую привязку |
| `authenticate(access_token)` | Возвращает `Principal(account_id, session_id, authenticated_at)` |
| `refresh_session(refresh_token)` | Однократная ротация; повторное предъявление отзывает всю сессию данного устройства |
| `revoke_session(access_token, all_sessions=...)` | Немедленно отзывает одну или все сессии аккаунта |
| `linked_providers(access_token)` | Возвращает только названия связанных провайдеров |
| `api/auth/dependencies.py` | Строгая FastAPI dependency `get_authenticated_user_id`; не доверяет `X-User-ID` |
| `api/migrations.py` | Отдельные транзакционные миграции `76` (foundation) и `77` (durable challenge), функция `run_auth_migrations(database)` |
| `scripts/migrate_auth.py` | Явный инструмент оператора: по умолчанию только инспекция, применение через `--apply` |
| `api/routers/auth_v2.py` | HTTP boundary: Telegram Mini App, Telegram bot challenge, Google OAuth state/nonce/PKCE, token refresh/logout |
| `app/src/store/useAuthStore.js` | Выбор Google/Telegram, хранение токенов, одноразовый обмен challenge и возобновление polling |

`VerifiedIdentity` — внутренний объект между проверяющим адаптером и сервисом.
**Нельзя создавать его из полей HTTP-запроса**, из тела webhook без аутентификации источника,
из `initDataUnsafe`, `localStorage`, URL или старого шестизначного кода.
Маршруты auth v2 зарегистрированы в `api/main.py` под `/api/auth/v2`; access/refresh никогда не помещаются в URL.

Проверка Telegram: HMAC сырого `initData`, уникальность полей, `auth_date`, тип и диапазон
ID, срок подтверждения 5 минут, допуск будущего времени 30 секунд. Повторно использованный
отпечаток не принимается, даже при перестановке параметров URL.
[Протокол Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Проверка Google: подпись, issuer, единственный ожидаемый audience, `azp` из серверного
списка разрешённых клиентов, срок, `iat`, `sub` и nonce. Сетевое получение сертификатов
ограничено timeout 10 секунд на запрос. `client_id`, разрешённые Android presenters и
ожидаемый nonce задаёт сервер, а не клиент. Сырые токены не записываются в БД или ошибки.
[Проверка ID token Google](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

## Сессии и транзакции

Токены непрозрачные, с 256 битами случайности. Access действует 15 минут, сессия и refresh —
максимум 30 дней от входа. Обновление не продлевает абсолютный срок и не обновляет дату
подтверждения личности. Для привязки необходим вход не старше 5 минут и свежая проверка
добавляемого провайдера. После истечения требуется повторный вход в текущий аккаунт.

При каждом access проверяются срок токена, отзыв сессии и отключение аккаунта. Старые access
после ротации живут до своего срока; отзыв сессии блокирует все её access/refresh сразу.
Повтор refresh сохраняет отзыв **до** возврата ошибки; чужие устройства сохраняют свои сессии.
[Обоснование ротации и отзыва](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

Сервис владеет транзакцией и закрывает соединение, если открыл его сам. Вызывать из синхронного
FastAPI handler либо переносить всю операцию в один worker. Внешняя транзакция запрещена:
иначе обработчик ошибки мог бы откатить отзыв сессии после повторного refresh.
Порядок блокировок PostgreSQL: аккаунт, затем сессия; уникальные индексы разрешают гонки привязок.
SQLite-тесты используют `BEGIN IMMEDIATE`. При гонке первого входа в PostgreSQL проигравшая
транзакция может получить `identity_conflict`; весь созданный ею аккаунт откатывается.

Клиент должен сериализовать refresh одной сессии, включая несколько вкладок. Автоматический
повтор после неопределённого сетевого исхода приведёт к отзыву; безопасный выход — новый вход.
Нельзя пропускать refresh через универсальный механизм повторов запросов без этого контракта.

Нужна задача очистки перед релизом: удалять истёкшие сессии каскадно и истёкшие proof-записи
небольшими пакетами. Использованные refresh сохраняются до конца жизни сессии для обнаружения
повторов; их нельзя удалять сразу после ротации. Просроченные access можно чистить отдельно.

## Сохранение существующих данных и миграции 76/77

Миграция `76` добавляет пять foundation auth-таблиц и запись истории. Миграция `77` добавляет
таблицу durable challenges. На каждый существующий
`TMAUser` добавляется `TMAAuthAccount` с тем же `user_id`. Другие строки не меняются.
Положительный `user_id` с `is_guest = false` записывается как **кандидат** на старую Telegram-привязку.
Никакие проверенные identities, токены или сессии при миграции не создаются.

Первый криптографически проверенный вход Telegram с этим `subject` сохраняет старый account ID
и создаёт identity. Флаг `is_guest` сам по себе не подтверждает личность: в старом API его можно
было менять. Миграция не может восстановить утраченное доказательство происхождения старых данных.
Подозрительные исторические записи требуют проверки до открытия мигрированного сервиса.

Старые гостевые ID случайные и могли совпадать с настоящими Telegram ID. Для такого совпадения
ядро возвращает `legacy_account_review_required` и сохраняет данные. Простое знание guest ID
не даёт права переносить его серверные данные. Восстановление гостя — отдельный процесс;
локальные колоды на его устройстве можно предложить импортировать с явным подтверждением.

Применение — отдельное техническое окно при переключении приложения: остановить старые записи
аккаунтов и старые входы, проверить резервную копию, выполнить миграцию, проверить инварианты,
запустить согласованные новые backend и клиенты. Если старые аккаунты продолжали создаваться
после миграции, нужен отдельный проверяемый backfill; повторный запуск `76` не сканирует их заново.

Инструмент берёт только явно заданный `AUTH_MIGRATION_DATABASE_URL` из окружения процесса.
Значение `SUPABASE_DB_URL` и `.env` не выбирают цель миграции. Использовать отдельный PostgreSQL
для проверки и TLS-параметры, подходящие целевому серверу; DSN не передавать аргументом CLI.

```powershell
# После явной настройки AUTH_MIGRATION_DATABASE_URL на выбранную тестовую базу:
python scripts/migrate_auth.py
python scripts/migrate_auth.py --apply
python scripts/migrate_auth.py
```

До/после проверять: число аккаунтов равно числу исходных пользователей; идентичностей и сессий
ноль; ID, количество и содержимое колод/карточек/прогресса/истории не менялись. В тестах сравниваются
также папки, коллаборация и офлайн-квитанции. PostgreSQL migration lock ограничен 5 секундами,
каждый statement — 60 секундами. Ошибка откатывает DDL, backfill и marker; повтор разрешён.
Неизвестные auth-таблицы без истории и пропавшие таблицы при наличии marker останавливают запуск.

Старый runner миграций записывает в историю даже ошибочные SQL; поэтому `76` намеренно
не входит в список `MIGRATIONS` и не запускается `create_all_tables()` или cold start API.
ID `76` зарезервирован: следующая миграция должна иметь другой номер.

Восстановление до включения auth v2: оставить добавленные таблицы и исправить причину ошибки;
основные данные не преобразованы. Если транзакция упала, она не оставляет частичную схему.
После появления Google-аккаунтов удалять таблицы или возвращать старую авторизацию нельзя:
это лишит пользователей привязок и вернёт известный обход доступа. Использовать исправление
вперёд или восстановление согласованной копии в техническом окне. Автоматического destructive down нет.

## Реализованный HTTP, бот, Android и UI

Реализованы следующие обязательные границы. Перед публикацией оператор должен выполнить
пункты deployment ниже и пройти ручной E2E на реальных провайдерах.

1. Durable challenge для `login` и `link` реализован миграцией `77`: случайный ID, provider,
   purpose, initiating session для link, hash секрета исходного устройства, OAuth state/nonce,
   PKCE S256 challenge, expiry, confirmed identity и одноразовое состояние выдачи результата.
   TTL 5 минут. Состояние хранить в PostgreSQL, не в памяти serverless-процесса.
2. Google включён через системный браузер. Для браузерного OAuth —
   точные redirect allowlist, state, nonce и PKCE; для native credential — nonce текущего challenge.
   Возврат в Android — verified App Link или разрешённая схема с одноразовым ticket,
   обмениваемым с секретом/PKCE исходного устройства. Access/refresh в URL не помещать.
3. Telegram Android/web использует challenge с непредсказуемым `/start` параметром,
   подтверждение действия и исходного устройства в боте. Проверить webhook secret до разбора
   Update; не подтверждать привязку просто по открытию чужой ссылки. Polling требует секрет
   исходного устройства, имеет expiry и одноразовый обмен. Числовой `guest_id` не является секретом.
4. Для Telegram Mini App обменивать сырое `initData` на сессию. Для link дополнительно связывать
   действие с текущей сессией и подтверждением пользователя. Одноразовый proof не заменяет
   проверку происхождения login/link challenge и защиту от login CSRF.
5. Проверка Google с сетью выполняется до транзакции. Внутри конечной сервисной операции
   блокировать, повторно проверять и потреблять challenge вместе с привязкой/сессией. Для этого
   не оборачивать её внешней транзакцией. Уникальный proof и одноразовый challenge потребляются
   атомарно.
6. Транспорт: web refresh в `HttpOnly; Secure` cookie с подходящим SameSite, точной проверкой
   Origin и CSRF; access в памяти. Android refresh — storage на базе Keystore, не обычный
   Capacitor Preferences/localStorage. Cookie и native token-response должны быть отдельными
   серверными контрактами; небезопасный режим нельзя выбирать произвольным client-флагом.
7. В одном согласованном переключении заменить `api/dependencies/auth.py` строгой dependency,
   все запросы клиента и sync — Bearer-сессией. Закрыть старые `/auth/session*`, `/auth/code/*`,
   доверие к URL `user_id`, миграцию из произвольного `guest_id`, ложную регистрацию по имени.
   Добавить распределённые лимиты challenge/login/refresh и лимиты размера запросов.
8. Перед включением убрать секреты и настройки других пользователей из `/api/init` с помощью
   явного списка клиентских настроек. Админские действия должны проверять серверный principal.
   Убрать произвольный повтор auth-мутаций в middleware `api/main.py`.
9. Адаптировать `api/routers/bot.py`, `api/services/reminder_service.py`: получать Telegram
   subject через identity, не через account ID. Новое сообщение боту должно обновлять профиль
   найденного аккаунта, а не создавать дубликат `TMAUser(user_id=telegram_id)`.
   Исправить numeric lookup в `api/routers/collaborative.py` для новых signed account IDs.
10. UI: равноправные «Google»/«Telegram», «Уже пользовались Lerne? Выберите прежний способ входа»;
    в настройках — связанные способы и «Добавить Google/Telegram». При `identity_conflict`
    предложить вход в прежний аккаунт, не выполнять автоматический merge.
11. До сетевых запросов восстановить/получить сессию. Удалить авторитет URL/`initDataUnsafe` из
    `getUserProfile`; профиль брать с сервера. При смене аккаунта остановить предыдущие sync,
    очистить только отображаемое состояние/кэш, не потерять pending Dexie edits. Разделять
    данные по каноническому `user_id`; не допускать записи позднего ответа прошлого аккаунта.
12. Unlink/удаление аккаунта требуют недавнего подтверждения. Последний способ входа нельзя
    отвязать. При unlink Telegram не восстанавливать его legacy-кандидата. Для удаления учитывать
    общие ресурсы и несинхронизированные данные; FK уже отзывают auth-сессии при удалении профиля.

HTTP-контракты:

| Метод | Вход и результат |
| --- | --- |
| `POST /auth/v2/challenges` | provider/purpose; для link текущая сессия; выдаёт challenge с клиентским секретом |
| `POST /auth/v2/telegram/mini-app` | raw initData + проверенный контекст; выдаёт сессию |
| `POST /auth/v2/challenges/{id}/exchange` | секрет/PKCE устройства; одноразовая выдача сессии или результата link |
| `POST /auth/v2/refresh` | cookie/native refresh; новый access и ротированный refresh |
| `POST /auth/v2/logout` | текущая сессия; отзыв, необязательный logout-all |
| `GET /auth/v2/identities` | текущая сессия; подключённые провайдеры |

Ошибки: `401` — отсутствующая/истёкшая сессия, proof или требование reauth;
`409 identity_conflict` / `provider_already_linked` — конфликт привязки;
`409 legacy_account_review_required` — неоднозначная старая запись;
`503` — провайдер не настроен/недоступен. Не возвращать чужой account ID или профиль при конфликте.

## Два уже заполненных аккаунта

Готовое ядро намеренно возвращает конфликт. Настоящий merge — отдельная операция и последующая
миграция: недавние независимые подтверждения обоих аккаунтов, явный выбор основного и предпросмотр.
Нельзя использовать старую `merge_guest_data`: она удаляет одноимённые колоды и карточки.

План merge должен учитывать `TMA_Folder`, `TMA_Deck`, `TMA_Card.creator_id`, `TMAProgress`,
`TMAReviewHistory`, `TMA_Collaborator.user_id/added_by`, `TMACustomPrompt`, `TMAUserPrompt`,
`TMAFeedback`, пользовательские ключи `TMASetting`, identities и офлайн-квитанции `TMAOfflineBatch`.
Одноимённые колоды сохранять; конфликт прогресса одной карточки решать по явному правилу с сохранением
истории. Если у обоих аккаунтов уже есть Google/Telegram, заранее согласовать итоговый набор привязок.

Сервер блокирует оба аккаунта в стабильном порядке, выполняет перенос и сохраняет alias/receipt
идемпотентного merge в одной транзакции, отзывает старые сессии. Клиенты переводят очереди и локальные
ID по выданным mapping; старый account ID не становится способом обойти аутентификацию.
Без этого протокола объединение двух заполненных аккаунтов не публиковать.

## Deployment checklist и пределы результата

Перед включением в production задать только через secret manager: `BOT_TOKEN`,
`TELEGRAM_WEBHOOK_SECRET`, `BOT_SETUP_TOKEN`, `REMINDER_CRON_TOKEN`, `PUBLIC_API_BASE_URL`,
`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_REDIRECT_URI`,
`TELEGRAM_BOT_USERNAME`. `GOOGLE_OAUTH_REDIRECT_URI` и `PUBLIC_API_BASE_URL` должны быть HTTPS;
redirect URI должен в точности совпасть с зарегистрированным в Google. Вызов `/api/bot_setup`
требует `X-Internal-Setup-Token`, а Telegram webhook — секретный заголовок Telegram.

Клиент сейчас хранит v2 refresh в localStorage ради совместимости существующего web/Capacitor
приложения. Перед публичным релизом Android должен перенести его в Keystore-backed storage, а web
— на отдельный cookie-контракт с CSRF/Origin защитой. Это известное ограничение, не выдавать его
за готовую защиту от XSS.

В UI реализован выбор Google/Telegram и безопасная повторная авторизация по тому же provider.
Экран управления привязками (`GET /auth/v2/identities`, `linkProvider`) подготовлен в store, но
его отдельная настройка и unlink намеренно не публикуются до UX-подтверждения/re-auth.

`python -m unittest discover -s scripts/tests -p test_auth_foundation.py -v` — 29 проверок:
сохранность данных, повтор миграции, откат при ошибке, FK/uniqueness, legacy-гость, Telegram → Google
на том же аккаунте, конфликт привязки, replay proof, ротация и параллельный refresh, отзыв, expiry,
изоляция соединений, строгая HTTP dependency, действительные и поддельные подписи провайдеров.
Google RSA-подписи проверяются реальной библиотекой; сертификат подставлен локальный, запросов нет.
Отдельно проверяются retired legacy header/code paths и одноразовый challenge exchange.

Выполнены `py_compile` изменённых Python-файлов и просмотр генерируемого PostgreSQL DDL
(в частности, account FK остаются BIGINT). Фактический PostgreSQL DDL/row-lock/concurrency
не запускался: изолированный PostgreSQL/DSN не предоставлен, psql/postgres/docker в PATH нет.
SQLite concurrency не доказывает поведение PostgreSQL; перед релизом повторить там миграцию,
rollback и гонки первого login/link/refresh. Production DB не подключалась.

Реальные Google/Telegram redirect, webhook и Android APK не проверялись: для них отсутствуют
тестовые provider credentials и устройство. OAuth-конфигурация, native secure storage и реальное
объединение двух уже заполненных аккаунтов остаются следующими работами. Выполнена production
сборка frontend; предупреждение Vite сообщает о большом существующем JS chunk, а не об ошибке auth.
